Build add-ons for WoW Forever

WoW Forever runs classic content on a modern client, with modern restrictions. Norgannon's add-ons solved those problems once, and share the answers in two layers. Use the one that fits what you're making.

LibForever: Forever's problems, solved for any add-on

LibForever-1.0 is a small library any add-on can embed, whoever wrote it. It's the code Norgannon Core runs on, so every Norgannon add-on tests it on every build. These are the walls add-on authors hit first on Forever, and its answer to each.

The problem What LibForever gives you
Classic functions are gone: GetSpellInfo, GetItemInfo, GetContainerItemInfo, UnitAura, the old quest log calls and dozens more. LF.Compat: about 60 of them, with their classic answers, through the client's new calls. No globals are written, so other add-ons are left alone.
Version checks misread the client, so libraries take the wrong path. LF.Client: IsForever(), Flavor() and IsClassicWorld(), from the interface number.
Health is always secret, and about 90 values turn secret in combat, so comparing or doing maths on them throws an error. LF.Secret, LF.Plain and LF.Call: read what can be read, and leave the rest to the client without an error.
Protected calls fail in combat. LF:AfterCombat holds them until combat ends, and LF:Restricted tells you which restriction is on and when it changes.
Characters have first and last names, so whispers to the name an event gave you can fail. LF.Names: who someone is, and the full name a whisper reaches, learned from chat, the guild roster and add-on messages.
Add-on messages are blocked during chat lockdown, and chat lines from add-ons may not reach chat in instances. LF.Net: compressed messages that wait for the lockdown to end, then go. LF:Say: when a line won't post, the chat box opens with it ready to send.
Saved settings need defaults and upgrades between versions. LF:SavedVars: defaults filled in, and upgrades run in order.

Download LibForever 1.0.1, or copy LibForever-1.0 from ForeverAPI's lib folder. Put it in your add-on's libs folder with LibStub, CallbackHandler-1.0 and AceComm-3.0, which come with it. Load them, then LibForever-1.0.xml. If several add-ons ship a copy, the newest one runs. The quick start has the full steps.

local LF = LibStub("LibForever-1.0")
LF:On("PLAYER_LOGIN", "MyAddon", function()
  local name = LF.Compat.GetSpellInfo(8936)
  LF:Print(name, "MyAddon")
end)

It's under the MIT licence: copy it, change it and ship it in your own add-on, free or not. Its bundled libraries keep their own licences. Bug reports and pull requests are welcome on ForeverAPI's GitHub page.

Coming: a port scanner that lists what an old add-on needs to run on Forever, and a test kit to run an add-on outside the game.

What Norgannon Core adds

Norgannon Core runs on LibForever and gives every LibForever call a Core name (Core.Compat, Core.Names, Core:AfterCombat and the rest), so the table above works the same in a Norgannon add-on. On top of it:

  • One call to start. Core:NewAddon gives you the version check, saved variables with defaults and migrations, a slash command with help, a settings page, and a row in the Norgannon minimap list and the game's add-on menu.
  • The family look. Windows, lists, settings rows, buttons, inputs and colours that match every Norgannon add-on, with fonts that cover nine languages.
  • Bars and auras that work in combat. UI.UnitBar draws health and power without reading the secret numbers, and UI.UnitAuras shows a unit's buffs and debuffs, drawn by the game inside a frame of yours.
  • The map. Pins on the world map and the minimap, a compass across the top of the screen and a waypoint arrow, shared by every add-on, so they never fight over the same pins.
  • The game data, if you want it. Searches by name, quest and loot helpers over NorgannonDB. The Core runs without NorgannonDB, so add-ons that don't need the data don't pay for it.

Reading the game data

NorgannonDB, the game data, is an ordinary add-on with a written format, the database specification. You don't need the Core to read it:

-- TOC:  ## OptionalDeps: NorgannonDB   (or ## Dependencies: NorgannonDB)
local DB = NorgannonDB
if not DB or not DB:RequireSchema(1, 4) then return end

local quest = DB:Get("quests", 783)      -- A Threat Within
print(quest.name, quest.level)

Field names and meanings are stable within a major schema version, and new data only ever adds. NorgannonDB is free software under the GPL-3.0, because it contains data from QuestieDB. If you copy its data into your own add-on, that data stays under the GPL. Found something wrong or missing? Players can help fix it, and so can you on NorgannonDB's GitHub page.

Where to start

For any Forever add-on:

  1. What the client allows: what WoW Forever's client forbids, which values are secret, and how to work with them. Read this before you trust anything you know from retail or Classic.
  2. LibForever's quick start: embed it and make your first calls.
  3. The Forever API reference: the client's own functions, events and widgets, as recorded in the game by a probe add-on rather than guessed from other clients. It includes a table of where each classic function went, and definitions for VS Code's Lua extension that flag calls that go secret in combat, are forbidden or are protected.
  4. Database specification: NorgannonDB's tables and fields, if you read the game data.

For a Norgannon add-on:

  1. Getting started: a working add-on in two files, and the rules Norgannon's own add-ons follow.
  2. Core API: every function the Core promises to keep. Anything not listed there is internal.
  3. NorgannonTemplate: a small, complete add-on to copy from. Norgannon's tests load it on every build, so it always works with the current Core.

Help improve the Forever API reference

The Forever API reference is recorded in the game by ForeverAPI Probe, an add-on for add-on developers. It notes how the game's functions behave: what kind of value each one gives back, which turn secret in combat, which calls fail, and the order events arrive in. It records shapes only, never the values themselves and never names.

  1. Download the probe from ForeverAPI's release, and switch on the parts you care about with /fapi.
  2. Play, or run the code you're working on, as usual.
  3. Type /fapi export, copy the text, and attach it to an "API data" issue on ForeverAPI's GitHub page.

Data from other people shows as reported, with a count, until Maro's own run confirms it or two different people's data agree. One file never marks anything as confirmed.

Versions

LibForever keeps its major version in its name: nothing in LibForever-1.0 is removed or changed, and a breaking change would be a new LibForever-2.0 beside it. If several add-ons ship a copy, the newest one runs.

A Norgannon add-on asks for the Core version it was written for: api = { 1, 20 } means "written for Core 1.20". It runs on any later 1.x, because a minor version only ever adds. A new major version may change things, and the Core says so in chat rather than failing quietly.
